# 上游版本选择性同步

本机制通过 GitHub Actions 评估并选择性引入 [QuantumNous/new-api](https://github.com/QuantumNous/new-api) 的版本变化。所有实际改动进入独立分支和 Pull Request，由维护者审查后决定是否合入；工作流不自动合并主分支，不部署业务服务，也不提供平台管理页面。

## 来源与版本语义

- 初始 fork 来源始终是 `v1.0.0-rc.26` / `8f6961c675932f406260ff0c218bc2aa0603e9b2`，见 [UPSTREAM.md](../UPSTREAM.md)。评估更高版本或迁入部分功能不会覆盖这个历史事实。
- 目标上游 tag 会解析并固定到完整提交 SHA；同一个 tag 后续指向其他提交时，原计划不能继续执行。
- 评估目标表示本批次研究的范围；每项决定和实施结果保存在计划及历史记录中。未完成的评估不能宣称已完整评估目标版本。
- 采用若干上游功能属于选择性同步，不代表完整升级到该上游版本。
- 下游 `VERSION` 延续 `v1.0.0-rc.26-novamaas.N` 格式，实际实施批次递增下游修订号。评估报告自身不修改版本。

## 使用前准备

先将同步工具及工作流通过 PR 合入默认分支，再从默认分支手动运行。不要从未经审查的分支运行带写权限的工作流。

在仓库 **Settings → Actions → General → Workflow permissions** 中允许 GitHub Actions 创建 Pull Request。GitHub 将创建和批准 PR 合并为同一设置；本机制只创建 PR，不批准、不启用自动合并。默认令牌权限保持只读，发布 PR 的独立 job 才申请 `contents: write` 与 `pull-requests: write`。

如组织策略禁止创建 PR，维护者需先处理该策略。工作流报告和执行附件仍用于排查；不要把个人访问令牌写入源码、计划或补丁。

## 第一步：评估指定版本

在 **Actions → Upstream sync · Assess version → Run workflow** 输入：

| 参数 | 含义 |
| --- | --- |
| `target` | 上游已存在的版本 tag，例如 `v1.0.0-rc.44`；不是浮动的 `main` 或任意仓库地址 |
| `range_base` | 评估范围起点，默认初始 fork 提交；第一次保持默认值 |
| `batch` | 本批次唯一标识，仅使用小写字母、数字和连字符 |
| `next_version` | 实际实施后使用的下游版本，例如 `v1.0.0-rc.26-novamaas.3`；必须高于当前修订号 |

评估读取固定范围内的上游提交、文件变化、本仓库自初始 fork 以来的文件修改、已有来源记录和补丁等价证据，输出：

```text
docs/upstream-sync/plans/<batch>/plan.json
docs/upstream-sync/plans/<batch>/report.md
```

结果通过评估分支上的草稿 PR 保存，并在 Actions 中提供摘要和附件。**评估 PR 只用于编辑计划，不能合入 main。** 本仓库现有流水线会在 main PR 合并后发布构建；完成实施后关闭评估 PR，实际来源记录随实施 PR 一并进入主分支。

报告是基于代码变更的初步证据清单。每个来源提交默认形成一项候选，可在计划中补充功能名称及分组。一个功能涉及多个候选时，应明确它们的依赖和采用范围。文件重叠、路径风险和补丁等价提示不能证明行为兼容，也不能代替计费、权限、协议或数据库语义审查。

后续批次可从已完成评估的上游提交开始。报告会带入历史处理证据，并单列新范围之外仍需跟进的暂缓、不采用及部分迁移项；缩小扫描范围不会自动补齐这些历史差异。

## 第二步：保存处理计划

在评估 PR 的分支编辑 `plan.json`，或检出该分支后提交修改。保留上游仓库、tag、SHA、范围起点、下游起始 SHA、候选来源和文件证据；这些字段执行时会重新核验。修改目标、范围或下游基线应重新生成评估。

逐项确定以下 `decision`，并写明 `reason`：

| 值 | 含义 |
| --- | --- |
| `pending` | 尚未判断；存在此项时不能执行 |
| `merge` | 原样采用该来源提交，通过 cherry-pick 保留来源 |
| `migrate` | 只迁入明确范围的行为，使用维护者准备并审查过的适配补丁 |
| `upgrade` | 采用属于协同升级的来源提交；相关项以依赖关系组成完整范围 |
| `skip` | 本批次不采用，记录业务或兼容性理由 |
| `defer` | 暂缓，记录阻塞条件及后续处理方向 |
| `covered` | 本仓库已有等价实现，提供代码、PR 或测试证据 |

`dependencies` 引用其他候选 ID；采用项的前置依赖必须已采用或有等价实现证据。执行器不会暗中增加选中范围。

`migrate` 需要把适配补丁提交到同一个评估分支，在该项填写 `patch.path` 和 `patch.sha256`，将 `selected_scope` 改为 `reviewed_patch`，并在 `evidence` 中解释实际迁入范围。补丁存放于 `docs/upstream-sync/patches/`；可用以下命令计算指纹：

```bash
sha256sum docs/upstream-sync/patches/<adaptation>.patch
```

macOS 可用 `shasum -a 256`。补丁应包含真正要迁入的代码和必要回归测试，不包含任意执行命令。上游一个提交混合了无关重构时，适配补丁只引入已经确定采用的部分，并写明部分迁入的范围。

所有候选都需要明确处理结论。对未采用项可以统一暂缓，但必须记录实际理由；不能把未审查内容默认判定为兼容或已覆盖。仅有 `skip`、`defer` 或 `covered` 而没有实际采用项的计划，不产生应用版本升级。

## 第三步：执行与验证

在 **Actions → Upstream sync · Apply plan → Run workflow** 输入：

- `plan_ref`：保存已审查计划及补丁的评估分支，或其完整提交 SHA。
- `plan_path`：`docs/upstream-sync/plans/<batch>/plan.json`。

工作流读取一次计划并固定其提交。它重新检查上游 tag、候选范围、下游 main 的起始提交、版本、依赖和补丁指纹，在独立工作区应用选定项。

执行中不允许来源改动写入 CI 工作流、同步工具、仓库规则、许可证或来源管理文件；来源和版本文件由工具统一更新。已有 New API / QuantumNous 的身份和署名信息必须保留。对涉及这些文件的混合上游提交，可以准备仅包含允许范围的适配补丁；需要修改治理或 CI 本身时，应另开人工维护 PR。

验证包括真实前端类型检查、测试和生产构建，根 Go 模块构建及测试，以及 `relaykit` 在 `GOWORK=off` 下的独立构建和测试。验证过程没有仓库写权限，也不使用生产连接和发布凭据。它不会启动本地 Docker。

改变数据库、计费或鉴权等核心行为时，维护者仍需补齐对应的回归测试与跨数据库验证。通用流水线通过不代表已经证明所有 SQLite、MySQL 和 PostgreSQL 业务行为等价。

任一步失败会保留诊断附件，不发布实施 PR。修正计划或补丁后重新执行；如果 main 已前进，需基于新 main 重新评估，不能继续使用旧基线假设。

## 第四步：审查实施 PR

验证成功后，独立发布 job 保存实际代码、计划、评估报告和历史回执，更新 `UPSTREAM.md` 与下游 `VERSION`，创建实施 PR。PR 使用仓库模板，保留需要人工填写的确认项，并说明自动化参与情况。

维护者审查：

1. 实际差异是否等于选定范围，必要的下游能力是否保留。
2. 适配项是否准确描述“实际迁入了什么”，没有把部分迁入写成整个提交或版本已升级。
3. 验证结果是否对应本次候选代码，业务边界是否有直接证据。
4. 是否形成长期核心运行时差异；如符合标准，由作者和评审按 [README 台账规则](../README.md#novamaas-与上游差异) 维护真实 PR 条目。同步工具不替代这一判断，也不把台账录入变成 CI 合并门禁。

工作流不合并 PR。主分支只有在维护者实际合入实施 PR 后才包含新版本、来源和历史记录；之后沿用现有发布流程。生成的实施 PR 会在后续更新时核验当前 HEAD 及来源记录。需要额外修改实施代码时，应把修改纳入已审查补丁并重新执行计划；直接追加代码或改写历史回执不能沿用旧的验证证据。

历史记录位于 `docs/upstream-sync/history/<batch>.json`，保留目标版本、上游提交、每项决策、实际迁入结果和验证证据。同批次不能重复应用；新的需求使用新批次，撤销时通过新的修复或 revert PR 保留历史。数据库和账务数据的恢复需按该变更的兼容方案处理。

## 本地检查工具

同步脚本仅依赖 Python 3 标准库，工具回归检查不需要运行业务服务：

```bash
python3 -m unittest discover -s .github/scripts -p 'test_upstream_sync*.py' -v
python3 .github/scripts/upstream_sync.py --help
```

本地使用 `analyze` 需要先获取目标上游 tag，`apply` 会创建独立候选工作区，不直接改写调用者的工作目录。完整调用参数以各子命令的 `--help` 为准。
