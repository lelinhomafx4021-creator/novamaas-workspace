# 历史消费有效金额与模型计费调账

实施日期：2026-10-09。本文记录本轮调账实现、资金边界及验收方法；与 [账单导出说明](BILLING_STATEMENT_EXPORTS.zh_CN.md)、[历史核验说明](BILLING_HISTORY_REVIEW.zh_CN.md) 配套使用。

## 1. 原始记录、有效金额与审计日志

调账保留原始消费/退款日志、任务计费快照、历史导入凭证、原始账务分录和上游成本快照。执行时新增关联到原始分录的修正分录，读取时计算：

```text
当前有效金额 = 原始金额 + 所有已执行修正分录 + 所有已执行撤销分录
本次差额     = 新规则重算金额 - 当前有效金额
```

用户的消费日志、按令牌查询的日志、日/月消费明细和小时汇总显示有效金额及有效计费组；管理员查看同一消费行也采用有效金额。原日志数据库中的原始金额不会被覆盖，不能因修改展示口径丢失资金凭证。普通用户不会看到独立的调账审计记录。

原有类型 8「费率调账」日志继续保留，用于记录执行/撤销时间、操作者、批次和差额；不删除已有日志。普通消费、收入和利润汇总排除独立类型 8，再把差额归入原消费/退款记录，避免同一差额计算两次。管理员明确筛选类型 8 时仍可按实际执行日期查询审计差额。

原始上游请求次数、token 用量和实际供应商渠道 ID 不变。首页原有 `quota_data` 图表是消费总额口径，只修正原消费行，不新增退款行；退款和净额在消费统计、日/月账目及正式对账单中体现。按客户计费组过滤的成本归属随有效消费行移动，以对齐该组的收入和利润；永久成本快照及实际供应商渠道归属保持不变。模型调账同时通过追加成本更正修复历史成本估算，有效成本为原快照成本加全部成本更正，详见第7节。

## 2. 历史对账单作废与重建

系统已有「作废对账单 → 创建新版本」流程，本轮复用该流程，并补上已确认账单存在后续调账时的提示。无需作废历史导入凭证。

1. 调账执行后，受影响的草稿、已下发或已确认账单提示存在未纳入的修正。
2. 管理员填写原因，作废受影响账单。
3. 为同一月份创建新版本，新版本按原消费/退款发生月份纳入最新修正，而不是把历史消费差额移到调账执行月份。
4. 重新归档、下发并由客户确认。

旧 PDF、Excel、明细、指纹、确认时间和确认回执仍保留。新版本冻结创建时的账务序号，后续调账或撤销不会修改已归档版本；需要再次作废并重建才能纳入后续变化。作废、重建和下载文件均不会再次扣除余额。

若旧版本曾按调账执行月份纳入差额，系统要求先作废该月份的旧版本，防止两个有效月份重复纳入同一笔差额。

## 3. 渠道变化调账与余额

界面名称为「渠道变化调账」，接口模式为 `group_rate`，旧客户端省略模式时继续使用该模式。

这里的渠道是客户计费组及其折扣比例。选择时间、模型和目标计费渠道后，沿用历史模型计费参数，变更组折扣；不会改变已经发生的实际上游供应商请求。若此前已经做过模型计费调账，则继承上次冻结的有效模型价格，避免恢复为旧价格。

执行按照批次净差额处理钱包：

| 净差额 | 钱包动作 |
| --- | --- |
| 大于 0 | 追加扣除余额 |
| 小于 0 | 退回余额 |
| 等于 0，但扣费/退款行或成本存在差异 | 修正账目或成本，余额不变 |
| 销售、成本及成本计价依据均无需更正 | 无需调账，禁止执行 |

完全退款的任务仍可能同时修正扣费和退款两侧，不能仅因净差额为零而禁止修正。余额不足、令牌额度不足或计数越界时整笔事务回滚，不会留下部分账目、部分扣款或已占用批次。

钱包、用户消费累计、令牌剩余额度/消费累计、渠道消费累计、修正分录和成本更正在同一主库事务内更新。钱包只处理销售净差额，供应商成本变化不会再次扣用户余额。重复确认同一已执行批次不会再次扣款或追加成本；撤销追加反向分录及成本更正，恢复对应资金和计数。对同一来源连续调账时必须先撤销后执行的批次，再撤销前一批次。

## 4. 模型计费变化调账

新增模式 `model_pricing`，界面选择时间和模型，无需选择目标计费渠道。重算使用当前模型价格以及每笔记录已有的有效计费组/折扣；此前已确认的渠道变化不会被覆盖。

- 区分任务提交扣费、最终差额结算及失败退款，按累计状态重算各来源分录，不直接按金额比例缩放已取整结果。
- 当前按次价格和 token 价格变化均可重算；当前计费方式决定是否进行 token 最终结算，不沿用旧「按次计费」标记。
- Seedance 优先使用已保存上游响应中的输出分辨率；响应未包含该字段时才读取归档请求。输入视频条件仍必须由完整输入请求证明，成功用量来自响应中的 `usage.total_tokens`。
- 优先读取独立请求归档中的实际 upstream 请求，其次原客户端请求，兼容旧任务内嵌请求。通用视频协议读取 `metadata` 中的选项，火山原生协议读取顶层选项。
- 请求省略分辨率但上游响应已明确返回受支持规格时，可以按已知输出重算；请求、响应都缺少分辨率时仍阻止。不把旧记录缺少 `video_input` 倍率当成「没有输入视频」，也不猜测缺失的分辨率。
- 失败且完全退款的任务无需成功响应 token 用量，仍可安全重算扣退两侧。

预览保存原始金额、当前有效金额、目标金额、行差额、有效组、目标组、价格参数、分辨率、输入视频条件、前一批次关联及证据指纹。新增独立的当前成本、重算成本、成本差额和成本折扣；利润变化等于销售净差额减成本差额。下载预览 JSON 不包含请求提示词、视频 URL、API 密钥或完整请求体。

响应中的 `resolution` 表示生成视频的分辨率，`usage.total_tokens` 是已计量的视频生成用量，见[火山方舟查询视频生成任务文档](https://docs.volcengine.com/docs/ark/get-video-generation-task-api?lang=zh)。按该用量乘对应单位价格及客户折扣，不再按时长或像素额外重复计算 token。

预览有效期为 15 分钟。确认时重新核对来源分录、任务状态、用量、计费配置和账务序号；任何相关变化都要求重新预览。只有超级管理员通过已登录会话与二次安全验证，并确认目标用户 ID 和净差额后才能执行。财务核算人员可查看页面和记录；跨账户操作仍要求管理员角色及财务核算权限。

### 可处理范围

当前调账范围为有完整任务及账务证据的已完成钱包异步任务，支持按次和 token 计费。订阅、未终结任务、表达式计费、普通聊天日志或缺少完整生命周期证据的记录会阻止整个批次，不会猜价后扣款。每批最多 20 个模型、93 天、1,000 条来源分录；应把同一任务的提交、结算和退款纳入同一时间范围。

任务状态为 `SUCCESS` 本身不能证明钱包结算已经完成：轮询会先保存终态，再写入差额。原 token 任务仅有提交预扣分录、任务额度仍为预扣金额且没有结算完成证据时，调账必须阻止，即使旧计费参数算出的最终金额恰好等于预扣。这样可以防止调账后原轮询再结算而重复扣退；原按次固定价任务的完整单行凭证不受此限制。

## 5. Seedance 2.5 分档价格

以下参考价格来自本次产品需求附件，单位为人民币/百万 token。分辨率及输入视频条件的倍率规则同时用于新请求和历史重算。

| 模型系列 | 分辨率 | 无视频输入 | 有视频输入 |
| --- | --- | ---: | ---: |
| Seedance 2.5 | 480p / 720p | 70 | 42 |
| Seedance 2.5 | 1080p | 77 | 46 |
| Seedance 2.0 | 480p / 720p | 46 | 28 |
| Seedance 2.0 | 1080p | 51 | 31 |
| Seedance 2.0 | 4k | 26 | 16 |

本轮为以下两个精确模型名接入 2.5 分档：

```text
doubao-seedance-2-5
doubao-seedance-2-5-260628
```

2.5 相对于无视频输入 720p 基准的倍率分别为 `1`、`42/70`、`77/70`、`46/70`。480p 与 720p 使用相同价格。2.0 的现有价格和 4k 规则继续保留；2.5 的 4k、未知或非字符串分辨率在新请求验证时返回 400，历史重算也拒绝未知组合。

平台的 `ModelRatio` 是可配置基准价，分档规则按该基准乘倍率。任何显式自定义价格都保留；如果配置了固定 `ModelPrice`，按平台现有优先级执行固定价。只有日期别名未配置时，才继承 `doubao-seedance-2-5` 已配置的基准倍率；若两者都未配置，采用代码默认值。公开价格列表与实际生效倍率保持一致。

例如汇率 7、基准 `ModelRatio=5` 时，基准为 `5 × 2 × 7 = 70` 元/百万 token。10,000 token、折扣 0.66、1080p 无视频输入的最终金额为 `77 × 10000 / 1000000 × 0.66 = 0.5082` 元；同用量的 720p 为 0.462 元，追加差额为 0.0462 元。实际执行以预览中冻结的整数 quota 为准，并处理提交/结算的取整边界。

## 7. 调账同步更正历史成本

历史成本是平台根据当时销售金额及客户折扣推算的估算，并非直接读取供应商账单。旧销售基数未使用分档倍率时，单独将渠道成本折扣改成0.82仍会保留错误的统一基数。模型计费调账现在独立重算销售金额与供应商成本，两者分别应用客户计费折扣及渠道成本折扣。

例如Seedance 2.5的10,000 token、1080p且包含输入视频，模型基准倍率5、渠道成本折扣0.82时，供应商净成本按46元/百万token计算，约0.3772元；不会继续按70元计算为0.574元。最终以完整任务生命周期的累计计价及整数quota取整为准。

### 成本证据与后续重算

原成本快照不覆盖，执行追加关联来源快照的成本更正，保存正确基数、预扣及结算前后累计基数、折扣、目标成本、批次和操作者。消费成本为正、退款成本为负；按累计状态计算后再取相邻状态的差，避免把每条退款单独取整造成净成本不一致。

成本更正直接归属原消费/退款发生月份。通用日志、财务汇总、日/月账目和利润读取原快照加追加更正。后续成本折扣重算使用已经修正的计价基数，不恢复原销售日志中的旧基数。渠道变化调账保持有效上游计价基数，客户目标组折扣不会替代渠道成本折扣。

当前渠道成本折扣已配置时使用该配置；当前渠道未配置而原成本凭证已有有效折扣时沿用凭证折扣。原渠道既无配置也无有效成本折扣的历史默认成本政策保持不变，不猜测供应商折扣。已配置成本却缺少可信来源快照时，预览阻止执行。

### 确认与撤销

证据指纹同时冻结有效成本、成本基数、折扣、最新成本更正及定价参数。确认前这些数据变化时要求重新预览。成本和钱包操作在一个事务中提交，任何一侧失败都会回滚。

零销售差额仍会留下关联原分录的批次事件，用于审计、连续批次依赖及历史账单版本检查，钱包余额不变。成本更正有独立追加凭证；无销售差额时不制造额外消费或退款日志。

撤销追加反向成本更正，恢复撤销前的有效成本、基数和折扣。若该来源已有后续调账或成本重算，应先处理后续依赖，不能覆盖后续结果。升级前已执行批次没有新增成本证据，继续按原资金范围撤销；其历史成本可由新的模型计费调账修复。

## 8. 直接调用与调账后的分档单价展示

Seedance 2.0、2.5 的实时计费已使用第5节的分辨率与视频输入分档。基础倍率与分档倍率分别保存，账户计费组折扣另行参与金额计算。例如基础70元/百万token、1080p无视频输入时，分档倍率为`77/70=1.1`，日志应显示77元/百万token；账户折扣0.86独立展示，不提前折入这项标准单价。自定义基础价格继续按原配置乘分档倍率，不强制覆盖为参考价格。

此前直接提交日志只在正文中写入两位小数的`video_input`，没有保存结构化倍率；普通结算日志将精确倍率放在顶层。调账返回日志则带有`other_ratios.video_input`和分辨率。前端只识别调账使用的结构，还要求`is_task`、`resolution`均存在，所以相同的1.1倍率会在直接调用中显示70、调账后显示77。77是已保存分档倍率参与展示后的单价；基础模型倍率未被折成77后再次乘1.1。

本次统一提交、结算、退款与调账返回日志的任务标识和结构化倍率。无附加倍率时保存明确的空对象`{}`。列表与详情共用同一解释逻辑：优先使用结构化倍率；只有该字段不存在的旧日志才读取顶层精确倍率。空对象表示倍率1，不能回退到遗留的1.1或0.6，否则恢复基础档位或撤销后会显示错误价格。普通任务详情也可展示已保存的精确分档倍率，不要求先调账。

已有提交日志在读取时可以批量关联原任务计费上下文，恢复保存的精确`video_input`。关联要求同一用户、唯一任务，以及模型、渠道、令牌、计费组、组倍率和已有模型倍率一致；结构化快照和旧顶层精确倍率已存在时不补写。不能从正文中的`0.66`重建`46/70`，不能查当前价格或从输出分辨率推造当时没有保存的倍率。缺少可信关联或快照时保持原展示。仅补充返回数据，不修改原日志、任务、quota、钱包或成本凭证，随后有效调账投影覆盖原提交倍率。

实时计费当前沿用提交请求提取的分档倍率；模型计费调账优先使用保存的实际输出分辨率。若请求与实际输出跨价格档位，调账可能产生真实金额差额。本次仅统一已保存计费证据的展示，没有新增按输出规格重新结算的收费规则，也没有因看到77而执行历史扣款。分辨率和视频输入标签只展示已有可信字段，不按倍率倒推出缺失的标签。

本次验证包括提交及结算的精确倍率、历史用户/管理员/令牌三个日志入口、跨用户或不一致证据不补全、调账空倍率覆盖旧值、原始数据及余额不变。Seedance 2.0 通用与火山原生请求路径还经过 HTTP JSON 解析、验证、预估计费及上游请求构造，覆盖两个模型别名、480p/720p/1080p/4k、有无视频输入的32个用例。前端实际点击日志列表进入客户详情，覆盖2.0的1080p/4k和两代模型的含视频/无视频档位，以及旧结算格式和重复倍率防护。
