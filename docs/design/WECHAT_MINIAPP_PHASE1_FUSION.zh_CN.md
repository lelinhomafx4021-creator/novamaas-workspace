# 微信小程序首阶段融合方案

日期：2026-09-27。关联项目计划 MP-710～715。本方案用于确定接口边界、账号归属和发布验收；各任务仍以项目计划中的状态为准。

## 2026-10-06 增补：短信验证、手机号登录与微信绑定管理（已实现，待外部联调）

本节记录新需求的开发方案。确认后，本节的手机号和微信身份规则取代下文首发阶段的“系统分配号码自动绑定”过渡规则；下文保留为历史方案。手机号范围和短信登录策略已于本次沟通确认，现进入实施与分阶段验收。

### A. 已确认范围

- 按顺序完成 Web 手机号绑定与登录，再完成小程序短信/微信手机号快捷登录，最后补齐绑定信息展示与管理。
- 手机号填入后须通过短信验证码核验，才能成为已绑定登录身份；用户可换绑。账号密码登录且启用 MFA 时，允许在认证器/备用码与绑定手机短信之间选择。
- 微信手机号与平台已验证手机号一致，且 AppID/OpenID 已归属于同一账号时，可走既有微信身份登录；尚未绑定的微信必须明确确认平台账号关联，不静默建立关系。
- 已确认：首期仅支持中国大陆 +86；短信快捷登录可直接完成登录，包括 MFA 账号；微信字段按接入要求设计并预留拓展，展示优化围绕绑定资料。
- 明确授权的业务规则：短信验证是独立登录方式，不重复要求认证器；密码登录仍可选择认证器/备用码或手机短信作为第二步。验证码用途隔离，不扩大到其他敏感权限。

### B. 当前实现与兼容边界

- `users.phone` 当前由管理员维护，`ValidateAndFill` 已支持账号、邮箱、手机号加密码登录；保留账号/邮箱优先级和原有密码验证、状态检查及登录开关。
- `verified_phones` 已存在，手机号与 user_id 双向唯一，记录验证来源和时间。复用该表作为可信归属，不批量认可历史 `users.phone`。
- `MiniAppPhoneLogin` 当前可凭微信授权匹配未经短信验证的系统分配号码，并对普通、无 MFA 账号自动建立绑定。新规则必须移除该自动绑定路径，回归测试相应更新。
- 现有微信验证产生的可信记录保留来源和时间，不标记为“已短信验证”；历史未验证号码展示为待验证。历史格式冲突、资料字段与可信归属不一致时禁止自动选择用户，提供管理员核对路径。
- 既有账号/邮箱密码、Passkey、OAuth、微信扫码服务、注册开关和计费体系继续按原规则工作。新短信能力默认关闭，配置缺失不影响原有入口。
- Web 的旧 `wechat_id` 与小程序身份不同，分别展示和管理；绝不能把小程序 OpenID 写入旧字段。

### C. 手机号绑定、换绑与管理员维护

1. Web 用户管理输入号码后显示待验证；发送验证码成功不等于绑定成功。新建用户可先保存账号和待验证号码，随后从该用户的绑定操作完成核验。
2. 个人账户安全页提供首次绑定和换绑入口。首次绑定要求当前登录会话、重新验证现有账号凭据，再验证新手机；仅持有新手机不能操作另一用户的账号。
3. 常规换绑先验证旧绑定手机，再验证新手机。旧号不可用时，通过现有密码及已启用的认证器/备用码或 Passkey 进行受控恢复；无可用验证手段时转管理员恢复，不提供匿名重置。
4. 管理员发起核验必须校验管理权限、目标角色、管理员近期安全验证，并绑定目标 user_id。验证通过前不覆盖已绑定号码；普通资料更新接口不能修改可信归属或绕过专用换绑流程。
5. 旧号不可用时，管理员用自己的近期密码、认证器或 Passkey 验证，再对目标的新号码进行短信核验和原子换绑；不先清空旧归属。操作记录审计并撤销目标会话，禁止“管理员填入即验证成功”。
6. 统一规范化号码后，在同一事务内消费挑战、校验最新用户状态/认证版本、检查归属、更新可信表和资料字段。绑定/换绑具有唯一约束，冲突不合并账号；失败保留原绑定。
7. 绑定身份变化推进 AuthVersion，撤销其他会话，按现有会话轮换服务保留经过验证的个人当前会话；管理员恢复撤销目标用户会话。更新鉴权缓存，旧挑战失效。
8. 手机号换绑不自动迁移或删除微信身份。新的微信手机号登录需重新满足同账号手机号匹配，冲突或不匹配时保留已有数据并走显式处理。

### D. 短信发送、挑战与登录

- 后端新增阿里云短信配置，使用官方 SendSms SDK，单号码发送。凭据通过服务端环境或安全配置注入，管理界面不回显密钥，公开状态仅提供可用能力布尔值。
- 配置项包含启用、AccessKey/RAM 凭据、可选 STS token、签名、模板 ID、验证码变量名；连接超时固定 3 秒、读取超时固定 5 秒。具体模板及变量名称待用户提供；未配置时接口明确不可用，不模拟成功。
- 验证码采用密码学安全随机生成的六位数；仅持久化带服务端密钥的摘要，绑定用途、号码、用户、会话或登录 flow、AuthVersion。挑战不能跨绑定、换绑、登录、MFA 场景使用。
- 实际配置：5 分钟到期、60 秒重发间隔、每挑战最多 5 次失败；号码/用户/IP 设小时和每日限额，另有全局发送预算。次数与限额更新必须原子化、多实例共享，不以进程内计数为唯一防线。
- 重发使同一操作的旧验证码失效；全局号码限额覆盖全部用途。发送失败/超时不能产生可验证的成功状态，禁止自动重试导致重复短信或绕过发送预算。限额不足、验证码错误和未知账号不泄露账号存在性。
- 成功消费验证码与账号状态变更在同一事务提交，失败次数在失败响应后仍保留；并发验证只允许一次成功。挑战表可复用 AuthFlow 的一次性语义，但验证码尝试次数及发送限额需要额外的持久状态。
- Web 的匿名短信发送保留 Turnstile；小程序发送须由服务端兑换新鲜 `wx.login` code，并记录其一次性消费、按 AppID/OpenID 增加发送预算，不要求原生客户端运行浏览器验证码。短信登录本身不产生微信绑定。
- Web 与小程序均提供独立“手机号 + 短信验证码”入口；只查询可信号码归属，未绑定号码不自动注册或绑定。MFA 账号同样可直接短信登录，遵循 A 节已确认规则。
- 密码登录后的短信第二步必须携带现有 2FA flow，只向该 flow 用户当前已绑定号码发送；服务端再次检查 AuthVersion、号码归属和启用状态，客户端不能指定接收号码或 user_id。
- 保留原认证器与备用码接口。短信登录第二步的授权仅限登录，不能顺带授予查看 Key、停用 MFA 等其他敏感操作权限。
- 所有成功登录仍使用既有服务端 Session/refresh 轮换、登录通知和审计，记录实际登录方法；验证码、微信 code、session_key、密钥不进入日志。

### E. 微信匹配、确认与解绑

| 微信身份与手机号归属 | 服务端结果 |
| --- | --- |
| OpenID 已绑定 A，微信手机号已验证归属 A | 按既有微信身份登录签发会话 |
| OpenID 未绑定，微信手机号已验证归属 A | 创建短效确认 flow，返回匹配账号名称、用户名和脱敏手机号，用于左右头像关系确认；用户明确确认后才绑定并登录 |
| OpenID 已绑定 A，微信手机号归属 B 或不匹配 | 拒绝快捷登录，不迁移手机号或微信，不合并账号 |
| 手机号只存在于未验证资料字段 | 终止手机号快捷流程，提示先到 Web 平台完成手机号验证与绑定，再返回小程序 |
| 平台账号已有同 AppID 的另一个 OpenID | 拒绝覆盖；先完成授权解绑，再重新绑定 |
| 手机号无平台可信归属 | 终止手机号快捷流程，不签发确认 flow、不进入已有账号关联或小程序注册；提示先到 Web 平台创建账号（如需）并绑定手机号 |
| 禁用/删除账号、微信失败、过期/重放 flow | 拒绝登录或绑定，不返回成功会话 |

- 确认 flow 的 AppID、OpenID、号码与匹配 user_id 来自服务端兑换结果，不接受客户端伪造身份字段。包含认证版本/归属快照，确认时重新校验，防止换绑、解绑或禁用后的旧 flow 重新绑定。
- 经微信服务端验证的手机号匹配平台已验证号码后，所有角色（含管理员、MFA 账号）均可明确确认建立绑定，不额外要求密码、认证器或备用码。确认、归属写入及 flow 消费原子提交，取消不产生绑定。
- 微信资料包含 AppID、OpenID、可选 UnionID、用户选择的昵称、持久头像数据、绑定及更新时间。OpenID 是身份依据，UnionID 无值时不阻断，昵称/头像仅作展示。
- 用户主动选择昵称/头像，可跳过且不阻断绑定。头像通过会话鉴权接口上传，最大 2 MiB、宽高不超过 4096、总像素不超过 1600 万；服务端重编码为最长边 256 的 JPEG，以数据库二进制字段持久保存，读取也需鉴权；不保存本机临时路径，不把任意客户端 URL 当作可信头像或由服务器任意抓取。
- 个人和管理员分别具备解绑入口；个人需当前会话与近期安全验证，管理员需目标角色权限、近期安全验证和操作审计。提前确认仍有可用登录方式，避免解绑最后一个凭据后锁死用户。
- 解绑仅处理指定 AppID 的小程序身份与资料，不影响旧微信扫码身份、手机、其他 OAuth 或业务数据。推进 AuthVersion，失效相关会话、旧登录挑战和确认 flow；当前微信登录会话须重新以独立凭据验证/登录。
- 解绑后同一微信再次授权，必须重新进入匹配和明确确认流程，不能通过旧客户端缓存或未消费 flow 恢复绑定。

### F. 展示与操作入口

- Web 个人中心：待验证/已绑定手机号、自有号码、核验时间、绑定/换绑；单独的小程序微信资料卡、绑定状态与解绑确认。
- Web 用户管理：手机号验证状态与核验动作、微信昵称/头像/绑定时间及受权限控制的 OpenID 详情；管理员解绑/恢复有明确影响说明。在选中用户的账号绑定详情中按需读取，避免列表逐用户查询。
- 小程序首页/我的：平台账号身份、微信昵称/头像、绑定状态。个人中心提供微信资料编辑/解绑；手机号核验/换绑从 Web 账号绑定入口操作；更改后重新读取服务端状态，不仅依赖本地登录缓存。
- 处理取消授权、资料未填写、头像失效、验证码过期/失败、倒计时、发送未就绪、禁用按钮、长昵称和不同屏幕尺寸。全部新增用户文案覆盖七语言。
- 展示优化围绕用户已确认的微信接入字段，不扩大到支付、媒体或对话改造。

### G. 实施顺序与验收

1. 先补现有未验证手机号自动微信绑定的回归用例；实现归属规范化、挑战与发送限额、事务与会话撤销，验证三库兼容。
2. 完成阿里云适配、配置、Web 绑定/换绑/管理员维护、手机短信登录及登录第二步选择。配置缺失场景和原登录流程都须通过测试，再进入小程序。
3. 小程序接入同一短信服务，改造微信匹配为一次性确认，补资料持久化和个人/管理员解绑。
4. 补首页/个人中心/Web 管理展示、七语言和行为回归，完成联调及部署说明。

验收用例必须覆盖：历史手机号不自动验证；多种格式相同归属及冲突；错误/到期/重发/重放/次数上限；发送失败和重复请求；不同用户/会话/用途挑战串用；并发抢占号码；旧号不可用的恢复；管理员越权；MFA 二选一及错误凭据；禁用/删除/认证版本变化；微信首次确认/取消/冲突/解绑后旧 flow；头像未选/上传失败；原密码、Passkey、OAuth、refresh 和计费回归。

后端运行受影响包测试和构建；若涉及 relaykit 公共 API，单独执行 `GOWORK=off go build ./...`。Web 运行受影响行为测试、typecheck、涉及文件 lint 和 build；miniapp 运行 typecheck、lint、test、build:weapp。不启动 Docker；MySQL/PostgreSQL 若没有现成测试连接，报告尚未执行的实库验收，不把 SQLite 通过当作三库已验收。

真实短信交付需审核通过的签名、模板、RAM 权限和测试号码；微信授权、昵称/头像、域名及解绑后重新登录需开发者工具与合法 HTTPS 域名下的真机验收。自动测试通过与外部联调通过分别记录。

发布按“Web 手机核验 → 小程序快捷登录 → 展示管理”逐步开启能力。回滚关闭新增入口但保留可信归属和安全拒绝规则，不恢复未验证手机号自动绑定；数据库迁移只做可兼容的增加，不删除业务数据。

依据：[阿里云 SendSms](https://help.aliyun.com/zh/sms/developer-reference/api-dysmsapi-2017-05-25-sendsms)（签名、模板、发送非幂等及返回语义）；[微信官方头像昵称组件说明](https://github.com/wechat-miniprogram/mp-user-avatar/blob/master/README.md)（主动选择资料与本地/持久存储边界）。微信开发文档直连当前不可访问，平台权限与实际回调字段仍须在真机联调中验证。

### H. 配置与验收记录（2026-10-06）

超级管理员配置入口为 **系统设置 → 身份认证 → 短信服务**（`/system-settings/auth/sms`）。支持保存访问密钥、签名、模板、验证码变量名及可选 STS 令牌；已保存的凭据不回显，留空保留原值，清除 STS 令牌须显式选择。通过 `GET/PUT /api/option/sms` 原子保存整组配置，启用前检查完整性；页面展示运行状态与环境变量覆盖项。已有部署环境变量继续优先，若要从后台开启，请移除显式的 `SMS_ENABLED=false`；参数也可按 `.env.example` 注入。首期使用单个验证码模板，`ALIYUN_SMS_CODE_PARAMETER` 对应模板变量名，默认 `code`。签名、模板需在阿里云审核通过，RAM 凭据需允许 `dysms:SendSms`；没有真实参数时保持 `SMS_ENABLED=false`。多实例须使用相同且稳定的 `SESSION_SECRET`、共享主数据库和现有会话缓存配置，以使挑战和发送预算跨实例一致；发送预算不依赖进程内计数。不把访问密钥、session_key、微信 code 或原始验证码写入日志/前端。

主要接口：

| 范围 | 接口 |
| --- | --- |
| Web 短信登录 | `POST /api/user/login/sms/code`、`/sms`；密码 MFA 替代验证为 `/sms/mfa/code`、`/sms/mfa` |
| 个人手机核验 | `GET /api/user/self/phone`；`POST /self/phone/security/code`、`/verify`、`/code`、`/bind` |
| 管理员手机核验 | `GET /api/user/:id/phone`；`POST /:id/phone/code`、`/bind`（管理员独立近期凭据） |
| 用户创建/更新时核验 | `POST /api/user/phone/code` 接收 `user_id`（更新）或 `username`（创建）、`phone`；创建/更新请求携带 `phone_challenge_token`、`phone_verification_code` 和管理员 `X-Security-Proof` |
| 小程序短信登录 | `POST /api/mini/auth/sms/code`（含 wx_code）、`/sms`；密码 MFA 替代验证为 `/sms/mfa/code`、`/sms/mfa` |
| 微信关联 | 既有 `/api/mini/auth/phone` 返回确认 flow；`/bind` 含 confirm_only 或账号凭据，身份参数完全由服务端生成 |
| 微信资料管理 | `GET /api/user/self/wechat-miniapp`、`/avatar?app_id=`；`POST /profile`、`/unbind`；管理员可通过 `/:id/wechat-miniapp` 查看、读取头像与解绑 |

创建或更新用户时，区号 `+86` 在编辑器中独立固定展示，持久化仍使用无空格的规范号码；个人资料显示区号与号码间的空格。手机号旁显示已绑定、待验证或未绑定状态，提供发送验证码按钮。新增/改动号码必须在最终保存时核验；未改动的历史资料号码允许保存其他资料且仍保持待验证，未改动的已绑定号码无需重复发码。旧绑定不能直接通过清空资料字段删除。

新增的 `user_mutation` 短信用途绑定管理员会话及凭据版本，创建时绑定草稿用户名，更新时绑定目标 ID 及凭据版本。验证码匹配、用户资料保存、可信号码归属变更和权限更新处于同一事务；错误、过期、跨号码、跨用户/草稿、跨会话、目标凭据变更或权限保存失败均保留原资料及归属。换绑/补核验后提升目标凭据版本并撤销旧会话。验证码错误返回表单验证状态（HTTP 400），避免误触发会话刷新退出。短信设置仅保留页面顶部保存操作，就绪状态使用绿色。

## 现状与目标

当前微信登录先通过 `wx.login` 换取 AppID 作用域内的 OpenID。已有绑定直接登录，未绑定则要求输入现有账号密码（含 2FA）或注册。`users.phone` 由系统管理员分配维护；它本身不能证明当前微信用户持有号码，但结合微信手机号授权的服务端验证，可以作为首发阶段的账号归属来源。Web 现有的 `wechat_id` 来自另一套扫码服务，与小程序 OpenID 不等价。

首阶段保持现有账号、会话、权限和计费体系。微信验证号码与系统唯一分配号码一致的普通账号，可以直接建立小程序绑定并登录；有 2FA 或管理权限的账号仍需原账号验证。手机号不会因数据库中有值就被批量迁移为可信身份，必须由微信实际验证持有后才建立独立归属记录。后续短信补绑服务再提供给 Web 和小程序。

已确认的首发策略：新小程序用户和使用微信手机号快捷登录的用户必须建立可信手机号归属；旧用户继续使用原有登录方式，逐步补绑。阿里云短信签名及模板目前尚未配置，短信补绑不纳入本次小程序发布阻断项，但不能把未完成的短信能力展示为可用，也不能要求旧用户立即完成补绑。

## 1. 手机号身份与登录（MP-710、711）

### 1.1 可信绑定

- 新建独立的已验证手机号归属记录，手机号和用户 ID 分别唯一，并记录验证时间、来源与状态。三种数据库均使用 GORM 可迁移的普通索引与唯一约束；不把多个空手机号放进唯一列。
- 旧 `users.phone` 作为系统分配的过渡期归属来源，仅在微信服务端验证手机号后用于唯一匹配。匹配时兼容中国手机号的本地、`86` 前缀与 `+86` 形式；存在多个匹配用户或与既有归属记录冲突时安全失败。批量迁移不自动认可旧值，也不因冲突合并用户。
- 已登录用户在账户安全页发起绑定或换绑。阿里云短信验证码绑定到操作、用户、手机号和短效挑战；服务端校验验证码、到期、尝试次数、发送频率与一次性消费。日志只记录脱敏手机号和请求 ID，不记录验证码、签名密钥或微信 code。
- 换绑属于高风险操作：要求当前会话及原有安全验证，完成后更新会话认证版本并撤销其他会话。管理员直接填写的手机号不会立即产生已验证归属；需微信持有验证或后续短信验证。
- 旧账号继续可使用现有登录方式补绑。是否把“未绑手机号”扩大为全站强制门槛，待历史账号补绑流程与客服恢复流程就绪后再开启，避免发布时锁死现有用户。

### 1.2 小程序快捷登录

1. 用户主动点击微信手机号授权按钮；取消授权时保留现有账号登录入口。
2. 小程序分别取得 `wx.login` code 和手机号授权 code，服务端分别兑换 OpenID 与手机号。两种 code 不复用、不存入客户端长期存储。
3. 如果 OpenID 已绑定用户，继续按该用户登录；手机号与其他已验证用户冲突时停止并提示人工核对，不修改现有绑定。
4. 如果 OpenID 未绑定，而微信验证号码唯一对应系统已分配的普通账号且无 2FA，原子地登记手机号与微信身份并登录。管理员账号或已启用 2FA 的账号必须继续走密码及 2FA 验证；身份归属不明确时不自动关联。
5. 新手机号只有在注册开关开启、用户接受协议且后端完成手机号可信绑定时才能创建用户。注册关闭、手机号冲突、用户封禁或微信接口失败都安全失败，不能退化为静默建号。
6. 登录成功继续签发当前可轮换的移动会话；请求层和 `/pg/chat/completions` 计费路径不变。

阿里云发送能力作为后续可关闭的服务端配置接入，使用专用 RAM 凭据、审核通过的签名和验证码模板。配置不就绪时不展示短信绑定入口，微信验证手机号和原有账号验证仍可使用；真实短信交付要在隔离环境和真实号码验证。

## 4. Web 扫码绑定与小程序确认（MP-715）

这应是独立于旧 `wechat_id` 的新流程，复用现有小程序身份表和移动会话。第一步在 Web 已登录的账户安全页生成一次性短效绑定挑战；小程序扫描后显示 Web 账号和设备摘要，明确确认才可绑定，同一微信身份或账号已有不同归属时拒绝。

第二步才是登录确认：Web 在密码验证后生成短效挑战，桌面显示一个随机提示码；已绑定、已登录的小程序扫描后在多个备选码中选择桌面上的码，并明确批准或拒绝。后端校验挑战、账号、会话、选码、到期、尝试次数和一次性消费，再把结果交给发起挑战的 Web 会话。扫码本身不签发 Web 登录态；跨账号、重放、过期、拒绝均不得成功。

当前 TOTP/备份码保留。若将小程序确认用作第二因素，必须由用户主动启用，并以密码已通过的登录流为前提；不能把“扫码登录”和“2FA 替代”混为一个隐式开关。Web Passkey 仍是独立可用的登录路径。

## 5. 对话作为简单问答入口（MP-714）

首屏围绕“提问—回答”排列：进入页面就可看见底部输入框与发送动作，后台加载默认可用模型，不要求用户先选模型或下滑；空状态示例问题点击即提问，并明确提示消耗账户额度。当前模型仅在顶部显示为简短入口，分组/模型选择按需展开，箭头使用固定尺寸的 CSS 图形保证居中。回答按段落、标题、列表、引用、代码块与行内强调解析为小程序原生节点，不注入模型返回的 HTML。收到回答后优先展示消息、继续提问、停止与重试；编辑放入次级操作。媒体任务仍从“用量”直达，不在对话页复制任务管理。

“新对话”创建独立本地会话，不再清空旧记录；历史入口可按最近更新时间切换或单独删除，删除前二次确认。原单会话 v1 草稿迁移到 v2 多会话存储，保留原每段消息数与字符限容规则；退出登录仍清除本机历史。历史仅保存在当前设备，不承诺跨设备同步或服务端追溯；本地空间不足时须提示保存失败。

本阶段只处理文本问答。流式传输、权限和计费规则不变；本地历史升级到 v2，多会话仍遵守原单段限容。图片上传、语音输入、联网搜索、多模态文件和服务端会话同步另立任务，不能以界面占位暗示已支持。

### 2026-10-06 手机号登录联调修正

手机号授权使用两种不同的临时凭证：`Taro.login()` 返回的 `code` 兑换 OpenID，`getPhoneNumber` 回调的 `code` 作为 `phone_code` 兑换手机号。`MINI_AUTH_CODE_INVALID` 表示第一步兑换失败，尚未执行手机号归属匹配。本次发现开发工具项目 AppID 与后端 `.env` 的 AppID 不一致，按用户确认以项目配置为准修正本地后端 AppID；向微信官方核对原有密钥返回 `40125`。用户在本地更新对应的 AppSecret 后，再次请求官方接口不再报告凭据错误；密钥不进入聊天或日志。

更新的小程序会从 `Taro.getAccountInfoSync()` 读取实际 AppID 并随手机号登录提交 `app_id`。后端只将其与已配置 AppID 比较，不用客户端输入选择凭据；不一致时返回 `MINI_AUTH_APP_ID_MISMATCH`（409），在消费任何微信 code 之前终止，并显示七语言配置提示。旧客户端未提交该字段时保留既有服务端微信兑换流程。空 code 不发送到后端；一次性凭证兑换失败不自动重发请求。微信 `40013`/`40125` 按配置错误处理，避免误报为临时 code 无效。

更新 `.env` 后须重新启动本地后端，在微信开发工具中重新编译并点击登录以取得新凭证；网络面板中旧的 code 不得重放。昵称/头像、可信手机号比对、首次确认、MFA 及微信解绑规则保持原方案。

本次已核对 3000 端口实际服务：当时仍运行其他工作树中的旧代码。确认数据库和会话配置一致后，改为启动当前工作区的已构建版本；在线检查错误 AppID 返回 409 `MINI_AUTH_APP_ID_MISMATCH`，正确 AppID 配合刻意无效的测试 code 返回 401 `MINI_AUTH_CODE_INVALID`，后者是预期结果，不能据此宣称真实授权成功。完整 Go 回归、后端构建、小程序 55 项测试、类型检查、lint 和微信构建均通过。微信开发工具应加载当前工作区 `miniapp/dist` 并重新编译，用新取得的真实登录及手机号授权 code 完成最后验收。

按后续验收反馈，将上一版普通昵称输入改为微信原生 `Input type="nickname"`，增加与头像按钮同样明显的“使用微信昵称”按钮。点击按钮聚焦昵称输入，并提示用户在微信键盘上方选择微信昵称；选中的昵称同步回填至左侧微信账号展示，确认绑定时随选填头像一起保存。使用原生昵称填写能力，不以手机号授权推断头像或昵称授权，不调用旧版资料接口自动获取昵称。头像与昵称仍可跳过，手机号匹配和绑定归属规则不变。
