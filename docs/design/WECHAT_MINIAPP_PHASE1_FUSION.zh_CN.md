# 微信小程序首阶段融合方案

日期：2026-09-27。关联项目计划 MP-710～715。本方案用于确定接口边界、账号归属和发布验收；各任务仍以项目计划中的状态为准。

## 现状与目标

当前微信登录先通过 `wx.login` 换取 AppID 作用域内的 OpenID。已有绑定直接登录，未绑定则要求输入现有账号密码（含 2FA）或注册。`users.phone` 由系统管理员分配维护；它本身不能证明当前微信用户持有号码，但结合微信手机号授权的服务端验证，可以作为首发阶段的账号归属来源。Web 现有的 `wechat_id` 来自另一套扫码服务，与小程序 OpenID 不等价。

首阶段保持现有账号、会话、权限和计费体系。微信验证号码与系统唯一分配号码一致的普通账号，可以直接建立小程序绑定并登录；有 2FA 或管理权限的账号仍需原账号验证。手机号不会因数据库中有值就被批量迁移为可信身份，必须由微信实际验证持有后才建立独立归属记录。后续短信补绑服务再提供给 Web 和小程序。

已确认的首发策略：新小程序用户和使用微信手机号快捷登录的用户必须建立可信手机号归属；旧用户继续使用原有登录方式，逐步补绑。阿里云短信签名及模板目前尚未配置，短信补绑不纳入本次小程序发布阻断项，但不能把未完成的短信能力展示为可用，也不能要求旧用户立即完成补绑。

## 1. 手机号身份与登录（MP-710、711）

### 1.1 可信绑定

- 新建独立的已验证手机号归属记录，手机号和用户 ID 分别唯一，并记录验证时间、来源与状态。三种数据库均使用 GORM 可迁移的普通索引与唯一约束；不把多个空手机号放进唯一列。
- 旧 `users.phone` 作为系统分配的过渡期归属来源，仅在微信服务端验证手机号后用于唯一匹配。匹配时兼容中国手机号的本地、`86` 前缀与 `+86` 形式；存在多个匹配用户或与既有归属记录冲突时安全失败。批量迁移不自动认可旧值，也不因冲突合并用户。
- 已登录用户在账户安全页发起绑定或换绑。阿里云短信验证码绑定到操作、用户、手机号和短效挑战；服务端校验验证码、到期、尝试次数、发送频率与一次性消费。日志只记录脱敏手机号和请求 ID，不记录验证码、签名密钥或微信 code。
- 换绑属于高风险操作：要求当前会话及原有安全验证，完成后更新会话认证版本并撤销其他会话。管理员直接填写的手机号不会立即产生已验证归属；需微信持有验证或后续短信验证。
- 旧账号继续可使用现有登录方式补绑。是否把“未绑手机号”扩大为全站强制门槛，待历史账号补绑流程与客服恢复流程就绪后再开启，避免发布时锁死现有用户。

### 1.2 小程序快捷登录

1. 用户主动点击微信手机号授权按钮；取消授权时保留现有账号登录入口。
2. 小程序分别取得 `wx.login` code 和手机号授权 code，服务端分别兑换 OpenID 与手机号。两种 code 不复用、不存入客户端长期存储。
3. 如果 OpenID 已绑定用户，继续按该用户登录；手机号与其他已验证用户冲突时停止并提示人工核对，不修改现有绑定。
4. 如果 OpenID 未绑定，而微信验证号码唯一对应系统已分配的普通账号且无 2FA，原子地登记手机号与微信身份并登录。管理员账号或已启用 2FA 的账号必须继续走密码及 2FA 验证；身份归属不明确时不自动关联。
5. 新手机号只有在注册开关开启、用户接受协议且后端完成手机号可信绑定时才能创建用户。注册关闭、手机号冲突、用户封禁或微信接口失败都安全失败，不能退化为静默建号。
6. 登录成功继续签发当前可轮换的移动会话；请求层和 `/pg/chat/completions` 计费路径不变。

阿里云发送能力作为后续可关闭的服务端配置接入，使用专用 RAM 凭据、审核通过的签名和验证码模板。配置不就绪时不展示短信绑定入口，微信验证手机号和原有账号验证仍可使用；真实短信交付要在隔离环境和真实号码验证。

## 2. 五个 Tab（MP-712）

继续使用微信原生 TabBar，保留文字以支持识别和七语言动态切换。首页、模型、对话、用量、我的各增加一枚简洁图标，灰色常态、紫色选中态。图标作为本地 PNG 打包，避免增加运行时图标库。开发者工具与真机需要验收图标清晰度、文案长度、暗色系统显示和选中态。

## 3. 媒体任务预览（MP-713、关联 MP-402）

图片和视频先使用现有带鉴权下载方法获取临时文件，再导航到独立预览页。页面同时提供系统返回与明确的“返回任务”按钮，返回后保留用量页任务列表状态。音频继续在任务卡中播放/停止。开发者工具中的返回行为不能代替真机结论；真机还须覆盖图片、视频、音频、错误文件、保存权限与域名校验。

## 4. Web 扫码绑定与小程序确认（MP-715）

这应是独立于旧 `wechat_id` 的新流程，复用现有小程序身份表和移动会话。第一步在 Web 已登录的账户安全页生成一次性短效绑定挑战；小程序扫描后显示 Web 账号和设备摘要，明确确认才可绑定，同一微信身份或账号已有不同归属时拒绝。

第二步才是登录确认：Web 在密码验证后生成短效挑战，桌面显示一个随机提示码；已绑定、已登录的小程序扫描后在多个备选码中选择桌面上的码，并明确批准或拒绝。后端校验挑战、账号、会话、选码、到期、尝试次数和一次性消费，再把结果交给发起挑战的 Web 会话。扫码本身不签发 Web 登录态；跨账号、重放、过期、拒绝均不得成功。

当前 TOTP/备份码保留。若将小程序确认用作第二因素，必须由用户主动启用，并以密码已通过的登录流为前提；不能把“扫码登录”和“2FA 替代”混为一个隐式开关。Web Passkey 仍是独立可用的登录路径。

## 5. 对话作为简单问答入口（MP-714）

首屏围绕“提问—回答”排列：进入页面就可看见底部输入框与发送动作，后台加载默认可用模型，不要求用户先选模型或下滑；空状态示例问题点击即提问，并明确提示消耗账户额度。当前模型仅在顶部显示为简短入口，分组/模型选择按需展开，箭头使用固定尺寸的 CSS 图形保证居中。回答按段落、标题、列表、引用、代码块与行内强调解析为小程序原生节点，不注入模型返回的 HTML。收到回答后优先展示消息、继续提问、停止与重试；编辑放入次级操作。媒体任务仍从“用量”直达，不在对话页复制任务管理。

“新对话”创建独立本地会话，不再清空旧记录；历史入口可按最近更新时间切换或单独删除，删除前二次确认。原单会话 v1 草稿迁移到 v2 多会话存储，保留原每段消息数与字符限容规则；退出登录仍清除本机历史。历史仅保存在当前设备，不承诺跨设备同步或服务端追溯；本地空间不足时须提示保存失败。

本阶段只处理文本问答。流式传输、权限和计费规则不变；本地历史升级到 v2，多会话仍遵守原单段限容。图片上传、语音输入、联网搜索、多模态文件和服务端会话同步另立任务，不能以界面占位暗示已支持。

## 6. 发布前验收顺序

1. 完成可信手机号绑定的三库迁移与账号归属测试；短信配置只影响后续短信补绑入口，不阻断微信验证手机号登录。在新旧账号、号码冲突、封禁、2FA 和会话重放场景下联调。
2. 以合法 HTTPS 域名、真实 AppID 和关闭调试校验的真机完成登录、问答、媒体预览/保存及五 Tab 验收。
3. 完成内容安全、隐私和审核材料、分包/性能以及体验版灰度；扫码确认登录的绑定与登录阶段各自独立验收。
4. 微信支付继续按 MP-520～523 的外部资质与商户配置处理，不以网页或客户端额度写入绕过。
