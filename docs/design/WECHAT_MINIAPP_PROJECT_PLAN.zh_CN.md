## 2. 状态约定与使用方式

- `待开始`：范围和验收标准已经确定，但尚未实施。
- `进行中`：当前已有实现工作，尚未满足全部验收条件。
- `待真机验收`：代码与自动化验证已完成，但必须在具备合法域名和真实微信环境的设备上完成最终验收。
- `已完成`：代码、测试、文档和验证均已完成。
- `阻塞`：存在无法在当前任务内解决的外部依赖，必须记录原因。
- `已取消`：经明确决策不再实施，必须保留取消原因。

后续任务可以直接使用稳定编号触发，例如：

> 开始执行 MP-103，并在完成后更新微信小程序项目计划。

执行规则：

1. 开始工作前，将目标任务标记为 `进行中`，记录实际开始日期。
2. 严格检查依赖任务；依赖未完成时，不得绕过核心安全或数据约束。
3. 完成代码后执行该任务列出的验收与测试。
4. 满足验收条件后标记为 `已完成`，补充完成日期和证据。
5. 任何范围变化都追加到“决策记录”和“变更日志”，不覆盖历史结论。

## 3. 产品目标

### 3.1 核心目标

- 为平台普通用户提供适合移动端的模型浏览、用量查看、对话、任务、钱包和个人中心体验。
- 使用微信原生登录、小程序网络和支付能力，同时复用现有用户、会话、计费、Relay 和任务系统。
- 保持 Web 管理台、微信小程序和后端业务规则一致，避免产生第二套计费或身份体系。
- 建立可测试、可灰度、可回滚、可持续演进的小程序发布链路。

### 3.2 首版非目标

- 不在小程序首版迁移渠道、模型元数据、用户、兑换码生成、系统设置等复杂管理界面。
- 不复用 `web/src/components`、Base UI、TanStack Router 或浏览器 DOM 组件。
- 不通过 WebView 包装现有管理台作为主交付方案。
- 不在客户端保存 AppSecret、微信支付私钥、`session_key` 或服务端管理凭据。

## 4. 已确认架构

```text
微信小程序（miniapp/，Taro + React）
├── 页面与轻量组件
├── 国际化与本地偏好
├── 小程序请求/流式传输适配
└── Access Token + 可轮换移动端会话
             │ HTTPS / Bearer
             ▼
现有 Go 服务
├── /api/mini/*：微信登录、移动会话、微信支付适配
├── /api/*：用户、模型、用量、钱包、订阅、账单
├── /pg/*：Playground Relay 与统一计费
└── service/model：复用会话、用户、计费、任务和日志能力
             │
             ▼
SQLite / MySQL / PostgreSQL + 可选 Redis
```

### 4.1 目录边界

```text
web/                 React 19 Web 管理台，独立依赖与构建
miniapp/             React 18 Taro 小程序，独立依赖与构建
api-contracts/       未来需要时增加，只允许纯类型/契约
controller/service/  两个前端共同使用的 Go 后端
```

- `miniapp/` 拥有独立 `package.json` 和 `bun.lock`。
- 小程序不得导入 `web/src`；跨端共享以 OpenAPI/DTO 或无运行时依赖的纯 TypeScript 契约为边界。
- 后端新增能力必须继续支持 SQLite、MySQL 和 PostgreSQL。
- Web 保持 React 19；小程序使用 Taro 官方支持的 React 18，不混合运行时依赖。

### 4.2 小程序信息架构

首版使用五个 Tab：

1. 首页：账户摘要、余额、订阅、今日用量、公告和快捷入口。
2. 模型：模型广场、价格、能力、可用分组和搜索。
3. 对话：移动端 Playground、流式响应和本地会话。
4. 用量：普通日志、图片/视频任务、账单与状态。
5. 我的：API Key、充值码、订阅、资料、登录设备和法律文档。

## 7. 跨任务质量门槛

### 7.1 前端

- 用户文案必须通过 i18n，覆盖 en、zh、zh-TW、fr、ja、ru、vi。
- 不使用浏览器 DOM、`localStorage` 或仅 Web 可用的组件；统一使用 Taro API。
- 避免大型 UI/icon barrel import；对重模块采用分包或延迟加载。
- 本地存储 key 必须带版本，只保存必要字段，并处理读取失败和迁移。
- 每个页面覆盖加载、空、错误、无权限、弱网和重试状态。
- 完成任务前至少运行受影响测试、`bun run typecheck`、`bun run lint` 和 `bun run build:weapp`。

### 7.2 后端

- 继续遵循 Router → Controller → Service → Model 分层。
- JSON 编解码必须使用 `common` 包装函数。
- 数据库代码兼容 SQLite、MySQL 和 PostgreSQL。
- 小程序请求继续经过现有鉴权、权限、计费、日志和限流边界。
- 登录、支付、API Key 明文等安全操作必须具有速率限制、审计和回归测试。
- 支付与额度变更必须幂等，禁止绕过现有 quota 安全转换和结算不变量。

### 7.3 发布兼容

- 小程序审核节奏慢于后端；后端必须至少保持一个已发布小程序版本的兼容性。
- 新能力通过 `/api/status` 或专用 capability 接口下发开关。
- 未配置或未获批准的登录、支付、生成能力默认关闭。

## 8. 风险登记

| 风险 | 影响 | 应对 | 当前状态 |
| --- | --- | --- | --- |
| React 18/19 依赖冲突 | 构建和运行时不稳定 | `miniapp/` 独立包与锁文件，禁止导入 `web/src` | 已控制 |
| 现有 `wechat_id` 语义不明确 | 错误合并或劫持账号 | 建立带 provider/appid 的独立身份表 | 已控制 |
| 小程序无法依赖 Web HttpOnly Cookie | 登录无法刷新 | 新增移动端专用轮换 Refresh Token 接口，不削弱 Web Cookie | 已控制 |
| 流式 chunk 被拆分 | 文本乱码或 SSE 解析失败 | 增量 UTF-8 解码与跨 chunk SSE 状态机测试 | 已控制 |
| 支付权限/类目不满足 | 无法上线充值 | 提前完成 MP-520，不以 WebView 支付绕过 | 阻塞 |
| 生成式 AI 合规材料不足 | 审核失败或服务风险 | 将备案、公示、内容治理列为正式发布前置 | 阻塞 |
| 小程序包体积过大 | 无法上传或首屏缓慢 | 直接导入、轻量组件、分包、资源预算 | 持续监控 |

## 9. 当前迭代

M1 微信身份与移动会话已于 2026-09-21 完成。小程序现在具有独立、可追溯的微信身份边界和可轮换移动会话；没有复用语义不同的旧 `wechat_id`，也没有在客户端保存 AppSecret 或 `session_key`。

M2、M3 与 M4 已于 2026-09-21 完成代码纵切。首次联调验收发现 M4 日志信息、媒体任务信息和首页账户摘要不足，随后重新打开 MP-200、MP-201、MP-400、MP-401 并完成二次实现。第三次体验改进完成 MP-212 与 MP-403：所有金额展示由 `/api/status` 的平台币种配置驱动，模型/套餐价格、充值额度和实付金额按各自语义换算；用量概览合并为单个紧凑区域，高级筛选默认折叠，普通日志与媒体任务改为“关键指标首屏 + 按需展开”的高密度卡片。除 MP-402 必须等待合法域名下的微信真机验收外，自动化质量门槛均已通过。

M0 工程基础交付如下：

- `miniapp/` 独立工程、`package.json` 与 `bun.lock`。
- 首页、模型、对话、用量和我的五个 Tab 页面骨架。
- 七语言国际化初始化、资源键一致性测试及动态标题/Tab 文案。
- 可配置 API 基地址的请求层、统一响应错误处理和 URL 测试。
- 首页 `/api/status` 加载、成功、错误、未配置和待初始化状态纵切。
- 路径触发的小程序 CI、开发约定与运行文档。
